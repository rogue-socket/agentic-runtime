# agentic-runtime — Gap Analysis

**Date:** 2026-03-16

---

## Context

The runtime has a solid execution engine: runs, steps, retries, branching, resume, replay, persistence, visualization, agent manifest packaging, LLM provider registry, and a full CLI. All of that is implemented and tested.

This document identifies what is **missing or incomplete** — the gaps between the current codebase and a product that developers can use to run real AI agents.

Gaps are ranked by severity: how much they block real-world adoption.

---

## Gap 1: No LLM calls (Critical)

**Impact:** Blocks all real usage.

The LLM registry exists. Providers can be configured in `runtime.yaml`. Credentials resolve from environment variables. But **no code actually calls an LLM API**. Every model-type step handler returns hardcoded stub output like `"Summary of: {issue}"`.

A developer who configures OpenAI, writes an agent, and runs `ai run my_agent` gets fake output.

**What's needed:**
- HTTP client adapter layer for OpenAI, Anthropic, and local/ollama endpoints
- A mechanism for handlers to request LLM calls through the runtime (not by importing `openai` directly)
- LLM calls treated as first-class runtime events (logged, metered, interceptable)

**Files involved:** `llm/registry.py` (exists, needs call layer), new `llm/adapters.py` or similar

---

## Gap 2: No built-in LLM handler

**Impact:** Critical — forces every developer to write custom Python for basic LLM steps.

A handler is currently `Callable[[RuntimeState], dict]` — a plain Python function. There is no bridge between declaring a model step in YAML and the runtime making an LLM call.

Developers expect to write:

```yaml
- id: summarize
  type: model
  handler: llm
  model: openai/gpt-4
  prompt: "Summarize this issue: {{ inputs.issue }}"
```

...and have the runtime handle the call. Instead, they must write a Python file, manage their own API client, and return a dict. The runtime adds no value over a script.

**What's needed:**
- A built-in `llm` handler type that reads `model` + `prompt` from the step definition
- Prompt templating using state paths (infrastructure exists: `format_template` in `utils.py`)
- Response parsing into step output dict

---

## Gap 3: Memory is pure scaffolding

**Impact:** High — no run-over-run learning or context retrieval.

Four memory tiers are defined (`WorkingMemory`, `EpisodicMemory`, `SemanticMemory`, `ProceduralMemory`). Interfaces exist. They're wired into the execution loop. But `hydrate_state()` and `persist_state()` are no-ops.

This means:
- No run-over-run learning
- No context carryover between steps beyond explicit state
- No long-term knowledge retrieval

**Pragmatic approach:** One tier that works is better than four that don't. Episodic memory backed by SQLite (already available) — persist past run summaries and make them queryable — would deliver immediate value.

**Files involved:** `memory/base.py`, `memory/episodic.py`, `memory/working.py`, `memory/semantic.py`, `memory/procedural.py`

---

## Gap 4: No streaming or progress feedback

**Impact:** High for UX — tolerable for CLI, blocking for programmatic use.

Every step runs to completion silently. For LLM-powered steps (5–30 seconds), the user sees nothing until the step finishes.

Missing:
- Streaming token output from LLM calls
- Step progress callbacks
- Real-time execution events beyond structured logs to stderr

For CLI usage this is bearable. For any programmatic embedding (API server, UI, notebook), it's a blocker.

---

## Gap 5: asyncio.run() in tool execution

**Impact:** High — known bug, will crash in async contexts.

`Executor._execute_tool()` uses `asyncio.run()` which raises `RuntimeError` when called from an already-running event loop. Consequences:

- Tools cannot execute from async contexts (FastAPI, Jupyter, etc.)
- The runtime cannot be embedded in async applications
- First developer who tries to use it as a library in an async app hits this

**Already flagged:** TODO comment in `core.py`

**Fix:** Detect running loop and use `loop.run_until_complete()` or refactor executor to be fully async.

---

## Gap 6: No useful built-in tools

**Impact:** Medium-high — every developer writes the basics from scratch.

One built-in tool exists: `EchoTool`. The tool protocol is solid, discovery works, but no practical tools ship with the runtime.

Developers expect at minimum:
- **HTTP/API call tool** — make external API requests
- **File read/write tool** — interact with the filesystem
- **Shell command tool** — execute system commands
- **Vector search tool** — query embeddings (when semantic memory exists)

Without these, every project starts by reimplementing common operations.

---

## Gap 7: No CLI input type handling

**Impact:** Medium — subtle bugs from string-only inputs.

All CLI inputs via `-i key=value` are strings. A step expecting a number gets `"5"` not `5`. A step expecting a boolean gets `"true"` not `True`.

Missing:
- Type coercion for CLI inputs (based on workflow input schema)
- Type declarations in workflow `inputs:` block
- Runtime type checking of step inputs/outputs

Current `inputs:` schema supports `description`, `required`, and `default` but no `type` field.

---

## Gap 8: No multi-agent or sub-workflow composition

**Impact:** Medium — limits to flat single-agent use cases.

Each agent runs one workflow. No mechanism for:
- One agent calling another agent
- A step invoking a sub-workflow
- Workflow composition (import/include steps from another workflow)

Real agent systems often have orchestrator agents delegating to specialist agents. The manifest system already notes this: "TODO: Support multiple workflows per agent with a designated entry point."

---

## Gap 9: No authentication or authorization

**Impact:** Low for local dev, blocking for shared/production use.

No access control exists:
- Anyone with CLI access can run any agent, read any run, resume any run
- No user/role concept
- No run ownership
- No API key scoping (which agents can use which providers)

Acceptable for local development. Blocks any shared deployment, multi-tenant use, or production scenarios.

---

## Gap 10: Minimal expression language for branching

**Impact:** Low-medium — forces workarounds for non-trivial conditions.

Branch conditions use `safe_eval` restricted to `state` and `len`. Cannot express:
- String operations (`state.inputs.priority.startswith("P")`)
- Numeric comparisons with coercion
- Collection membership tests
- Any non-trivial logic without writing a custom handler to set a boolean flag

The current restriction is intentional (security/determinism), but it pushes complexity into handlers for decisions that should be expressible inline.

## Recommended priority order

For shipping to early adopters:

| Priority | Gap | Rationale |
|---|---|---|
| **P0** | Gap 1 + 2: LLM calls + built-in handler | Without this, the product cannot do what it's named for |
| **P0** | Gap 5: asyncio fix | Small fix, removes a crash-level defect |
| **P1** | Gap 6: Built-in tools (HTTP, file, shell) | Eliminates boilerplate for every new project |
| **P1** | Gap 3: Episodic memory on SQLite | One working tier delivers real value |
| **P2** | Gap 7: Input type coercion | Small quality-of-life improvement |
| **P2** | Gap 4: Streaming/progress | Required before any non-CLI integration |
| **P3** | Gap 10: Richer expression language | Convenience, not blocking |
| **P3** | Gap 8: Multi-agent composition | V2 feature |
| **P3** | Gap 9: Auth model | Only needed for shared/production deployment |
