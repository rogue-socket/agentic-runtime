# agentic-runtime — Status Report

**Date:** 2025-07-18

---

## Summary

`agentic-runtime` is a runtime for AI agents — not a framework or library, but the execution substrate agents run on. It provides deterministic execution, full state tracking, failure recovery, and portable agent packaging.

This document captures the current state of every subsystem, what is implemented, what is scaffolding, and what is planned.

---

## 1. Architecture overview

The runtime executes YAML workflow definitions into durable run records with SQLite persistence. The execution model is step-sequential with conditional branching, retry/backoff, and deterministic resume/replay.

**Core flow:**
1. Load workflow definition (from file, registry, or agent manifest)
2. Create run record + initial state snapshot
3. Execute steps sequentially with retry/branch logic
4. Persist step records and state versions after each step
5. Mark run terminal (COMPLETED, FAILED, or COMPLETED_WITH_ERRORS)

## 4. Error hierarchy

All exceptions inherit from `RuntimeErrorBase(Exception)`:

| Exception | Trigger |
|---|---|
| `WorkflowValidationError` | Invalid workflow YAML |
| `StepExecutionError` | Step handler/tool failure |
| `ToolNotFoundError` | Tool name not in registry |
| `HandlerNotFoundError` | Handler name not in registry |
| `BranchResolutionError` | No matching branch rule and no default |
| `RunNotFoundError` | Run ID not in storage |
| `ReplayDataMissingError` | Incomplete data for replay |
| `ReplayMismatchError` | Replayed state diverges from recorded |
| `WorkflowIntegrityError` | Workflow YAML changed since original run (blocks resume) |
| `AgentValidationError` | Agent manifest invalid or missing dependencies |

## 5. Key features detail

### 5.1 Workflow hash lock on resume

When a run is created, the workflow YAML hash is stored in the `Run` record. On `ai resume`, `Executor.resume()` compares the stored hash against the current workflow hash and raises `WorkflowIntegrityError` if they differ. This prevents resuming against a modified workflow.

**Files:** [core.py](../src/agent_runtime/core.py) (`Executor.resume()`), [errors.py](../src/agent_runtime/errors.py)

### 5.2 LLM provider registry

Central registry for managing multiple LLM providers (OpenAI, Anthropic, local, etc.) with per-model configuration. API keys are resolved exclusively from environment variables — never stored on disk.

**Capabilities:**
- Register/lookup providers and models
- Credential health check (`check_credentials()`)
- Load from `runtime.yaml` `llm:` section
- Per-model config: temperature, max_tokens, extras

**Not yet implemented:** Actual HTTP clients for LLM API calls. Model-type step handlers currently return deterministic stub output.

**Files:** [llm/registry.py](../src/agent_runtime/llm/registry.py), [config.py](../src/agent_runtime/config.py)

### 5.3 Agent manifest system

The portable unit of the runtime. An `agent.yaml` declares everything an agent needs: workflow, handlers, tools, LLM providers, env vars, and default inputs.

**Capabilities:**
- Load and parse manifests (`load_agent_manifest()`)
- Pre-flight validation: file existence, provider availability, env vars, credential checks
- Export as `.tar.gz` archive (manifest + workflow + handlers + tools)
- Import from archive with post-import validation
- Agent-aware run resolution: `ai run <agent_id>[@version]`
- Default input merging (manifest defaults < CLI `-i` overrides)
- Path traversal protection in import

**Files:** [agent/manifest.py](../src/agent_runtime/agent/manifest.py), [agent/packaging.py](../src/agent_runtime/agent/packaging.py), [cli.py](../src/agent_runtime/cli.py)

### 5.4 State model

Namespaced state (`inputs`, `steps`, `runtime`) prevents cross-step key collisions and preserves ownership. `RuntimeState` manages reads, writes, snapshots, and diffs.

### 5.5 Retry and backoff

Per-step retry policy: configurable `attempts`, `backoff` (fixed/exponential), `initial_delay`. Retry state (`attempt_count`, `last_error`) is captured in `StepExecution`.

### 5.6 Conditional branching

`next` rules with `when` expressions evaluated top-to-bottom. Expression evaluation is constrained via AST validation (only `state` and `len` allowed). Default fallback supported.

### 5.7 Step contracts

Declared `inputs` (reads) and `outputs` (writes) per step. Workflow-load-time validation catches future-read and output collision errors. Runtime enforcement checks output keys against declared contract.

### 5.8 Deterministic replay

`ai replay` reproduces a historical run by injecting recorded state transitions without calling handlers/tools. Optional `--verify-state` checks reconstructed state matches recorded `state_before`.

### 5.9 Visualization

Three modes: ASCII (terminal), HTML (browser), and timeline (text). Powered by graph/timeline builders that reconstruct execution flow and state deltas from persisted data.

## 11. Roadmap priorities

Based on current codebase state:

1. **LLM API call adapters** — HTTP clients for OpenAI/Anthropic/local endpoints so model-type steps can make real LLM calls instead of returning stub output.
2. **Memory tier implementations** — Replace stubs with actual persistence (episodic), vector search (semantic), and retrieval logic.
3. **Multi-workflow agents** — Allow an agent manifest to declare multiple workflows with a designated entry point.
4. **Async event loop fix** — Replace `asyncio.run()` in `_execute_tool` with loop-aware execution to support embedded async hosts.
5. **DAG scheduler** — Parallel step execution for independent steps.
6. **Tool sandboxing** — Permissions and isolation policies for tool execution.
